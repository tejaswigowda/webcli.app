webCLI

Browser tools that take a URL and return an artifact. You open them with a GET and need no account. For the artifact tools your files never leave your device, and you can check that in DevTools; the paper explains the architecture. Tools that implement the agent surface below can be driven from a script.

The contract

URL in, artifact out. GET-only. Zero-egress. No account, no token, no upload. That is the contract for the artifact tools. An artifact is meant to be a pure function of its input URLs and parameters: that is verified by test for bodyrig (the worked example) and not yet checked for the others, and each card says which.

Zero-egress means your content is never sent anywhere: no request carries a body, a cookie or a credential. A tool may still fetch static code, model weights or the input URLs you name, by GET; each card lists exactly what under fetches. One live tool is a stream, not an artifact tool. It sits under Streams, outside this contract, and declares its own egress.

The agent surface

Not every tool has it yet; each card says whether it does, and agent in tools.json lists which.

A tool that implements it can be driven with no human in the loop:

  • run= in the URL query (or #fragment) starts the op as soon as the page loads.
  • window.__webcli_result holds the result: { ok, op, artifact, error, meta }.
  • [data-webcli-status] on <body> is the state: idle | running | done | error.
  • Stable data-testid hooks for the controls, listed on each tool's card.
// wait for the op to finish, then read the handle
await page.waitForSelector('body[data-webcli-status=done], body[data-webcli-status=error]');
const result = await page.evaluate(() => window.__webcli_result);

One worked example

For agents and scripts

The tool list on this page is rendered from one file. Fetch the same file directly:

curl -s https://webcli.app/tools.json
curl -s https://webcli.app/.well-known/webcli.json   # identical copy
curl -s https://webcli.app/tools.json | jq -r '.tools[] | select(.agent) | .origin'

Every tool declares kind (artifact or stream), egress (whether your content leaves the device), fetches (what it GETs on first use) and deterministic. Only the invariants live in the top-level contract.

The file carries "schema": 2. It is validated against schema/2.json; a breaking change bumps that number. Schema 1 (schema/1.json) had one global egress: "none" claim, which was not true for every tool; it is superseded. Every entry in tools is live: origin resolves and source is a public repository, or null when it is not public yet. agent: true means the tool implements run= and the result handle; params and result describe them.

Privacy and licences

The artifact tools process what you give them on your device: they do not upload it, need no account and set no tracking identifiers. Each tool's egress and fetches say exactly what it contacts; some load code or model weights by GET on first use. The stream tool, posecast, sends its stream to a websocket URL you supply, which by default is on your own machine; the zero-egress claim does not cover wherever you point it, and its card says so.

This page makes no request to any origin but its own, and a Content-Security-Policy enforces that; a CI test loads the page and fails on any other origin.

How the claim is checked. For a tool you can use today, bodyrig explains how to verify zero egress and its test suite asserts it. The worked example of the standard is the facebind privacy audit; facebind is not listed above yet because it is moving to its own origin first.

One planned tool would have a cloud tier. That is labelled under Planned above, and would be labelled on its card if it ships.
